> **Read this first.** Azure DNS zones have **no soft delete**. Deleting a private DNS
> zone deletes the zone and every record in it, and the operation cannot be undone.
> There is no portal "undelete" and no Microsoft-side restore. Recovery is limited to
> re-creating the zone and re-importing an exported zone file. Every step below is
> built around that single fact.

---

## 1. Objective

Identify private DNS zones across the Mercyhealth tenant that are demonstrably unused,
produce an evidence-backed deletion candidate list, and define a human-operated runbook
to remove them after approval.

A zone qualifies **only** when all three of the following hold:

| # | Criterion | Rationale |
|---|---|---|
| 1 | **Zero virtual network links** | An unlinked private DNS zone is not attached to any VNet's resolver, so it resolves for nobody. It is inert by definition. |
| 2 | **No record sets other than the auto-created apex default(s)** | Strict reading, per your decision. Any `A`, `AAAA`, `CNAME`, `MX`, `PTR`, `SRV` or `TXT` record set disqualifies the zone. The apex default is `SOA` (possibly also `NS` — see [§6a](#6a-the-record-set-baseline-contradiction-design-affecting)). |
| 3 | **Created more than 30 days ago** | Guards against deleting a zone that infrastructure code or policy created moments ago and whose links/records have not landed yet. |

Criteria 1 and 2 are yours as stated. Criterion 3 was added at your direction as a grace period.

**Explicitly not applied:** you asked for your two conditions only, so this plan does **not**
filter on private endpoint DNS zone groups, `deployIfNotExists` policy references, resource
locks, or infrastructure-code references. Those scenarios are documented in
[§11 Residual risk](#11-residual-risk) as decision inputs for the human approver rather than
as automated gates. That is a deliberate, recorded decision — not an oversight.

## 2. Scope

**In scope:** every subscription in the Mercyhealth tenant that the executing identity can
read, resource type `Microsoft.Network/privateDnsZones`.

**Out of scope:** public DNS zones (`Microsoft.Network/dnsZones`), DNS Private Resolver rulesets,
virtual network links belonging to zones that remain, and any zone failing any criterion.

**Coverage caveat (Confirmed, AGENTS.md §15):** Azure Resource Graph returns only what the
calling identity is authorized to see. An empty result set does **not** prove that no unused
zones exist — it may mean no read access. Reconcile the swept subscription count against the
expected tenant subscription count before treating the sweep as complete.

## 6. Confirmed findings, inferences, and unknowns

**Confirmed**

- The two stated conditions are fully testable from Azure control-plane data. No data-plane
  access and no DNS query logging are required.
- A pristine private DNS zone reports `numberOfRecordSets` of **1 or 2, never 0**, because the SOA
  record set is auto-created and cannot be deleted. A naive test for `numberOfRecordSets == 0`
  would match nothing and silently report a perfectly clean estate. This is the single most likely
  way to get this cleanup wrong.
- Deletion is irreversible, which places this work in Class 4 regardless of how empty the zones are.

### 6a. The record-set baseline contradiction (design-affecting)

Microsoft's own documentation conflicts on what a brand-new private zone contains:

| Source | Implication for a pristine zone |
|---|---|
| Supported record types are A, AAAA, CNAME, MX, PTR, SOA, SRV, TXT — no NS | baseline = **1** (SOA only) |
| Zone import guidance: "NS records must be removed prior to import" | baseline = **1** |
| ARG `dnsresources` indexes `.../privatednszones/{a,aaaa,cname,mx,ptr,soa,srv,txt}` — no `ns` type | baseline = **1** |
| `dns-private-records.md`: "the zone apex (name = '@') always contains the NS and SOA record sets during the creation of the zone" | baseline = **2** |

Three independent sources indicate 1; one sentence indicates 2, and it reads as boilerplate
inherited from the public DNS zone article. **This could not be settled from documentation alone,
and this session has no Azure access to test it empirically.**

Rather than bet on either value, the tooling was designed so the answer does not matter:

- The record-set **count** is used only as a loose pre-filter (`<= 2`), which cannot silently miss
  qualifying zones under either baseline.
- Eligibility is decided by record **type** — a zone qualifies only if it holds no record set
  outside the auto-created apex defaults, with both `SOA` and `NS` treated as defaults.

**Calibration step (do this once, before trusting any sweep).** Pick a private DNS zone you know
to be empty, or create one in a sandbox subscription, and observe the true baseline:

```powershell
az network private-dns record-set list -g <rg> -z <zone> --query "[].type" -o tsv
```

Record the result here so the next operator does not have to re-derive it:

> **Observed baseline for this tenant:** _(to be filled in at first run)_

**Inferred**

- Given the estate's heavy private endpoint usage, most `privatelink.*` zones are expected to be
  actively linked and therefore filtered out at criterion 1.
- Unused zones most plausibly accumulate from decommissioned spokes, abandoned proof-of-concept
  work, and duplicate zones created in spokes when a centrally-managed hub zone already existed.

**Unknown**

- How many private DNS zones exist tenant-wide, and how many qualify. Not yet enumerated.
- Whether ARG counter values are current for this estate. The prior networking review recorded
  that **ARG had indexing gaps for nested resources in this tenant and findings had to be verified
  via direct REST calls** (`chat-history/2026-07-21-tpa-prod-networking-security.md`). This is the
  single most important reason Stage 2 below re-verifies every candidate against the control plane
  instead of trusting the ARG snapshot.
- Whether the executing identity holds Reader across all subscriptions.

## 7. Implementation plan

### Phase A — Stage 1: candidate sweep (Class 0, read-only)

**A0. Calibrate the record-set baseline first** (§6a). One command against a known-empty zone,
recorded in this document. Skipping it does not break the tooling — eligibility is type-based —
but it tells you whether to expect `recordSets` of 1 or 2 in the report, and an unexpected value
is a signal worth understanding before you delete anything.

Then run the packaged script, which performs all three stages and writes a timestamped report:

```powershell
az login
az account show

./scripts/powershell/Get-UnusedPrivateDnsZones.ps1 `
    -ExpectedTenantId '7d689bf5-26f6-44a2-b080-61689eff65a6' `
    -MinimumAgeDays 30 `
    -Verbose
```

`-ExpectedTenantId` is a stop condition: if the active context is signed in to another tenant the
script exits before issuing a single query (AGENTS.md §5.3).

Reviewable query sources, if you would rather run them by hand in Resource Graph Explorer:

| File | Purpose |
|---|---|
| `queries/resource-graph/private-dns-unused-zones-candidates.kql` | Zones with 0 links and ≤1 record set |
| `queries/resource-graph/private-dns-unused-zones-recordset-proof.kql` | Joins `dnsresources` to prove the one record set is genuinely SOA |

### Phase B — Stage 2: authoritative verification (Class 0, read-only)

The script does this automatically for every candidate; the commands are listed so the evidence
is reproducible by hand:

```powershell
# Expect: []
az network private-dns link vnet list `
    --subscription <sub> --resource-group <rg> --zone-name <zone> -o json

# Expect: ONLY apex defaults - '.../privateDnsZones/SOA' (and '.../NS' if this
# tenant's baseline turns out to be 2, per §6a). Any A, AAAA, CNAME, MX, PTR,
# SRV or TXT entry disqualifies the zone.
az network private-dns record-set list `
    --subscription <sub> --resource-group <rg> --zone-name <zone> -o json `
    --query "[].{name:name, type:type}"
```

**Why this phase is mandatory.** ARG is a periodically-refreshed snapshot, and this tenant has a
recorded history of ARG lagging on nested resources. A zone linked five minutes ago can still show
`numberOfVirtualNetworkLinks = 0` in ARG. The control-plane call is authoritative; the ARG sweep
only narrows the field. **Never delete on ARG evidence alone.**

### Phase C — Stage 3: age gate (Class 0, read-only)

```powershell
az rest --method get --url `
  'https://management.azure.com/subscriptions/<sub>/resources?api-version=2021-04-01&$expand=createdTime,changedTime&$filter=resourceType eq ''Microsoft.Network/privateDnsZones'''
```

Zones created within 30 days are reported but marked ineligible. Cross-check anything ambiguous
against the Activity Log, which retains 90 days:

```powershell
az monitor activity-log list --offset 30d `
    --subscription <sub> `
    --query "[?operationName.value=='Microsoft.Network/privateDnsZones/write'].{time:eventTimestamp, resource:resourceId, caller:caller}"
```

### Phase D — review, soak, and approval (human decision point)

1. Circulate the generated `Output/<timestamp>-unused-private-dns-zones.csv`.
2. Confirm with the network/platform owner that no in-flight project depends on the listed zones.
3. **Soak for 14 days**, then re-run Phase A–C. A zone that qualifies on both runs is stable;
   a zone that changed between runs was never idle and must drop off the list.
4. Obtain explicit written authorization naming the exact zones (AGENTS.md §5.2).

### Phase E — backup before deletion (Class 0, mandatory)

Non-negotiable, because deletion cannot be undone. For every approved zone:

```powershell
$stamp  = Get-Date -Format 'yyyy-MM-dd-HHmmss'
$backup = "./evidence/private-dns-backup-$stamp"
New-Item -ItemType Directory -Path $backup -Force | Out-Null

# 1. Full ARM representation of the zone
az network private-dns zone show `
    --subscription <sub> --resource-group <rg> --name <zone> `
    -o json > "$backup/<zone>.zone.json"

# 2. BIND-format record export
az network private-dns zone export `
    --subscription <sub> --resource-group <rg> --name <zone> `
    -f "$backup/<zone>.dns"

# 3. VNet links (expected empty, captured as proof of the pre-state)
az network private-dns link vnet list `
    --subscription <sub> --resource-group <rg> --zone-name <zone> `
    -o json > "$backup/<zone>.links.json"
```

Store the backup outside the deleted resource's blast radius and verify each file is non-empty
before proceeding. `evidence/` is intended to be gitignored (AGENTS.md §18) — keep zone exports
out of source control.

### Phase F — staged deletion (Class 4, requires final authorization)

Delete in waves, never all at once:

| Wave | Target | Gate before next wave |
|---|---|---|
| 1 | One low-value zone in `dt-dev-*` | 48 h, no DNS or private endpoint incidents |
| 2 | Remainder of `dt-dev-*` and `dt-tst-*` | 7 days clean |
| 3 | `dt-prd-*` and connectivity hub zones | Change ticket + approved maintenance window |

```powershell
# CLASS 4 — DESTRUCTIVE, IRREVERSIBLE. Only after Phase E backup is verified
# and written authorization names this exact zone.
az network private-dns zone delete `
    --subscription <sub> --resource-group <rg> --name <zone>
```

Do **not** add `--yes` until final destructive approval is recorded (AGENTS.md §14). Deleting one
zone at a time, interactively confirmed, is the intended mode.

- Watch for delayed failures for 48 h — DNS breakage frequently surfaces only on the next client
  cache expiry or application restart, not immediately.

## 9. Rollback and recovery plan

| Element | Detail |
|---|---|
| **Trigger** | Any DNS resolution failure, private endpoint registration failure, or policy remediation error appearing after a deletion wave |
| **Decision owner** | Network/platform owner (to be named at approval) |
| **Maximum decision time** | 30 minutes from detection |
| **Known-good state** | The Phase E backup set |
| **Access path** | Azure CLI with Private DNS Zone Contributor on the target resource group |

**Rollback procedure**

```powershell
# 1. Re-create the zone with the SAME name in the SAME resource group and subscription
az network private-dns zone create --subscription <sub> -g <rg> -n <zone>

# 2. Re-import records if the export was non-empty
az network private-dns zone import --subscription <sub> -g <rg> -n <zone> -f "<backup>/<zone>.dns"
```

**Why rollback is unusually favourable here — and where it still falls short.**

An Azure resource ID is deterministic from subscription + resource group + name. Re-creating a zone
with the same three values reproduces the **identical resource ID**. Anything referencing the zone
by ID — a `deployIfNotExists` policy assignment parameter, a private endpoint DNS zone group, a
Bicep or Terraform reference — will resolve again once the zone is re-created. Combined with the
fact that a qualifying zone contains no records to lose, rollback is close to complete.

It is not, however, free:

- Private endpoints that attempted registration during the outage window do **not** retry
  automatically. Their DNS zone group must be re-applied, or the private endpoint re-created.
- Policy remediation tasks that failed during the gap must be re-run manually.
- Infrastructure-code state files (notably Terraform) will have recorded the deletion and may need
  a refresh or import to reconcile.
- **If the zone name, resource group, or subscription differs on re-creation, the resource ID
  differs, and every ID-based reference stays broken.** Re-create into exactly the original location.

**Where rollback is impossible:** if the Phase E backup was skipped or unverified and the zone held
records that were not captured, those records are unrecoverable — no Microsoft-side restore exists.
This is precisely why Phase E is mandatory and why the criteria restrict deletion to zones whose only
record is the SOA.

## 11. Residual risk

The criteria you selected are the two stated conditions plus the age gate. The following scenarios
pass those criteria but can still make a zone unsafe to delete. They are **not** filtered by the
tooling, by your decision, and are listed here so the approver in Phase D can weigh them manually.

| Scenario | Why it passes the criteria | Consequence if deleted | Suggested manual check |
|---|---|---|---|
| **Private endpoint DNS zone group** references the zone, but records were manually removed or the endpoint is disconnected | Zone genuinely has 0 links and only SOA right now | The private endpoint loses its DNS registration target; re-registration fails | `az network private-endpoint dns-zone-group list` on endpoints in related subscriptions |
| **`deployIfNotExists` policy** carries the zone's resource ID as a parameter (standard in Azure Landing Zones) | Policy-provisioned zones can sit unlinked and empty until a private endpoint appears | Every future private endpoint of that type silently gets no DNS; remediation fails | Search policy assignment parameters for `privateDnsZoneId` |
| **Infrastructure code** declares the zone | Code state is invisible to Azure control-plane queries | Redeploy churn, drift, or a pipeline that re-creates then re-deletes | `grep -ri "privatednszones" ` across Bicep/Terraform repos |
| **`CanNotDelete` lock** present | A lock does not alter link or record counts | Deletion fails harmlessly, but the lock signalled deliberate intent worth honouring | `az lock list --resource-group <rg>` |
| **Reverse-lookup (`*.in-addr.arpa`) zone** | Holds PTR records, which under a strict SOA-only rule correctly disqualify it | None under the strict rule you chose — this risk was eliminated by that decision | — |
| **Newly provisioned zone awaiting links** | Would otherwise qualify | Breaks an in-flight deployment | Mitigated by the 30-day age gate |
| **ARG snapshot staleness** | ARG showed 0 links while a link existed | Deleting a live zone breaks resolution for the linked VNet | Mitigated by mandatory Phase B control-plane re-verification |

Adding the first four as automated exclusion gates would be a small extension to the tooling if you
later decide you want them.
