01UnknownMonitoring

Two response-time alerts may be watching a dead metric

AverageResponseTime returns 0.00 on both apps at every aggregation, while HttpResponseTime returns real values from the same window. These are Windows App Services, where the older metric is not populated. Rules alert-response-time-frontend and alert-response-time-backend exist but their metric was not read in this pass.

Verify nextOpen both rules and confirm which metric they reference. Apply the same check to alert-cpu-time-frontend and alert-cpu-time-backend: CpuTime is absolute seconds, not a percentage, so a threshold written as if it were a percentage would also never fire.
02ConfirmedCost

The database is provisioned about a thousand times over

db-config is Standard S2, 50 DTU, holding 41 MB of a 250 GB ceiling. It ran at 0.10% DTU average and 5% peak, with data IO and log IO at a flat 0%, workers at 1.05% and about 2 concurrent sessions.

RecommendationReview against Basic or a serverless General Purpose tier. Confirm the retention, backup and SLA requirements the current tier may have been chosen for before proposing the change.
03InferredArchitecture

The application barely touches this database

The two apps served 321,268 requests over 239 successful database connections, roughly 1,344 requests per connection, against about 2 sessions. The name, the 41 MB footprint and the flat IO all point to a configuration store rather than the system of record. App Configuration and a storage account sit in the same resource group.

Verify nextConfirm where the TPA transactional data actually lives. If it is outside this subscription, this board covers only part of the workload's real dependency chain.
04ConfirmedChange

The 14 August release raised memory about 4.6x

Backend working set averaged 43 MB before 14 Aug and 199 MB after; frontend went 28 to 79 MB. Within each cycle the backend climbs roughly 60 MB over ten days then recycles, visible as drops on 18, 26 and 27 Aug. Plan memory average has drifted 29.6% to 31.2% across this window.

RecommendationNothing is at risk at 223 MB against a Premium worker, so treat this as a baseline to know rather than an incident. Worth confirming the step was expected from that release.
05ConfirmedLatency

Two separate blips on 4 September

Backend peaked at 11.65s in the 02:00 UTC hour and 1.19s at 03:00, with database connections jumping to 50 in the 03:00 hour against a 0 to 4 norm. Separately the frontend touched 1.67s at 05:00, which lines up with a site update recorded at 05:10 UTC and reads as a restart cold start.

Verify nextThe 02:00 backend spike has no deployment behind it. Check Application Insights failures and dependencies for that hour before dismissing it as a one-off.
06ConfirmedHealthy

Error and availability posture is clean

One HTTP 5xx across 321,268 requests. Database availability 100% every day, zero deadlocks, zero firewall blocks and one failed connection all week. HTTP queue length stayed at zero. A 404 burst on 5 Sep at 05:00 produced 222 4xx in one hour, then stopped.

NoteThe 5 Sep burst was 404 only, no 401 or 403, so it was not an auth failure. Requests doubled in that hour, consistent with a scan or a bad link rather than a fault.
