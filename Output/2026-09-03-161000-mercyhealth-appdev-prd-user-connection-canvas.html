dt-prd-tpa

TPA Application Landing Zones → Application Development → TPA Application

One domain, one Front Door Standard profile, two App Services split by path. The WAF here is correctly set to Prevention — but both App Services also carry an explicit "allow all" network rule, which means the front door is optional, not mandatory.

dt-prd-microsites

Microsites Landing Zones → Application Development → Microsites

There is no user-connection path to draw here. The subscription holds a spoke VNet peered to the hub and two platform-management resources — nothing else. Verified two ways: Azure Resource Graph and a direct az resource list both return the same three resources, and the account used has tenant-root Reader, so this isn't a permissions gap.

Findings

High

Both TPA App Services accept traffic that never touched Front Door or the WAF

app-tpa-prod-frontend-ncus and app-tpa-prod-backend-ncus each carry two IP restriction rules: Allow-FrontDoor (the intended one) and Allow all / Any (priority 2147483647 — last, but still an Allow). The second rule makes the first one decorative: *.azurewebsites.net is reachable directly, with no WAF inspection.

Contrast with the Connect Application apps in the same management group, which restrict to APIM's single IP with an explicit deny-all fallback — this is the pattern TPA should match.

High

The Premium Front Door's WAF is in Detection mode — it isn't blocking anything

WAFGlobalAzureManagedWithGeoRestrictionsAndRateLimiting, attached to afd-dts-global in front of the flagship Connect application, has policy mode Detection. It logs what it would have blocked but takes no action. The Standard-tier WAF protecting the smaller TPA app (wafprod) is correctly set to Prevention.

The more elaborately-named policy is the one not actually protecting anything — worth a deliberate decision rather than an oversight, given ten line-of-business apps sit behind it.

Note

Two TPA storage/config resources exist outside every traffic path

appcs-prod-fwubq55usdsyk (App Configuration) has public access disabled and no private endpoint reaching it — unreachable by any network path found. stfwubq55usdsyk (Storage Account) has no private endpoint and a default network rule of Allow — reachable, but not part of any confirmed app wiring. Both look like leftovers from an earlier provisioning pass.

Note

Connect Application's ten backend apps are well-isolated from each other and from the internet

Every one of the ten line-of-business App Services accepts inbound traffic only from APIM's public IP (172.214.234.155/32) with an explicit deny-all fallback — the opposite of the TPA finding above. This is the pattern worth standardizing on across the Application Development group.

Note

A test-tier App Service Plan lives inside the production subscription

asp-asp-hhs-test-ncus-test-ncus sits in dt-prd-app alongside the real production plans (its doubled name also suggests a templating mistake at creation time). It carries no traffic in the path traced here, but its presence in a prod subscription is worth a cleanup pass.

Note

Two shared-tier resources have weaker evidence than the rest of the diagram

pg-dts-shared-prod-ncus is network-isolated correctly (VNet-delegated subnet, public access disabled) but no managed identity in the subscription holds an RBAC role assignment on it — its consumer is unconfirmed. Separately, the DLQ function's own identity (uai-dlq-processor-prod) holds a role on Event Hub but none on the shared Storage account — so while the function is confirmed to consume from Event Hub, it is not confirmed to write to Storage. Storage's real callers are two other identities, one of which (uai-evh-audit-logs-dlq-prod) suggests audit-log may dead-letter independently rather than through the shared function.

Both are drawn with a dashed border to mark them honestly as unconfirmed rather than guessed — likely resolvable by reading the relevant Key Vault secrets or application code, neither of which this control-plane review opened.
