The two identity layers, per app

Managed identities (green) serve live user traffic. App registrations (amber) exist for a second, asynchronous purpose — Fabric pulling each app's data out for analytics. They are unrelated credentials serving unrelated paths; an app can have one, both, or neither.

Findings

High

One identity can write secrets to all eleven Key Vaults in the subscription

Object ID fcfaf24d-f685-4b6e-9827-1c75ebda655e holds Key Vault Secrets Officer — not just read — on every one of the ten app Key Vaults plus the platform kv-frontdoor-prod-ncus. It appears in neither the Enterprise Applications export nor a full tenant-wide User-Assigned Identity export (40 identities, all 22 subscriptions, checked row by row) — which rules out both classic app registrations and every user-assigned identity in the tenant.

That narrows it to one remaining possibility: a System-Assigned identity on a resource this review didn't enumerate — System-Assigned identities aren't independently listable, so no export catches them. The shape (one identity, write access, everything) still matches a CI/CD deployment resource — plausible and unremarkable if that's what it is. But it should have a name and an owner on record regardless. Resolving it now needs either a resource-by-resource identity sweep beyond Web/sites, ApiManagement, and Sql, or Microsoft Graph access.

Correction

The Postgres role I previously attributed to data access is a Defender role

spn-fabric-connect-prd's role on pg-dts-shared-prod-ncus is Defender Open Source Relational Databases — Microsoft Defender for Cloud's threat-protection role, not a data-read role. The shared Postgres server's actual data-plane consumer remains unconfirmed by RBAC, same as before this correction.

Note

Notification-service's real auth path is now visible — it's a classic app registration

Notifications App Prod resolves the gap flagged in the prior version of this review: app-notification-service-prod-ncus's managed identity carries no confirmed role on Event Hub, but a dedicated app registration exists with matching dev/test/prod counterparts. This is a name match from the export, not an RBAC confirmation — application configuration would confirm which credential the app actually uses at runtime.

Note

TPA authenticates through three unrelated identity systems

The managed identity id-prod serves live traffic. spn-fabric-tpa-prd feeds the Fabric analytics pipeline. tpa-kinde-production is a completely separate customer-identity platform (Kinde), unrelated to Azure RBAC. Three credentials, three purposes, three places a rotation or an incident response would need to check.

Note

No production Microsites app registration exists — independent confirmation of the empty environment

The export contains microsites-cms-dev and microsites-cms-test but no prod counterpart. This corroborates, from an entirely different data source, the earlier finding that dt-prd-microsites holds no deployed application.

App-registration data from a tenant-wide Enterprise Applications export (226 rows) supplied by the user, matched to workloads by name. Role definitions resolved via ARM roleDefinitions.
